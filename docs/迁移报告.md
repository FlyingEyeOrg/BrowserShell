## 四、迁移中发现并修复的缺陷

| # | 问题 | 成因 | 处理 |
|---|---|---|---|
| 1 | `internal sealed class Window : Window` 自继承，编译必错 | `DesktopWindow` → `Window` 撞 WPF `System.Windows.Window` | 裸 `DesktopWindow` 类改名 **`ShellWindow`** |
| 2 | Runtime 数十处 `CS0246` 找不到 SDK 类型 | 原命名空间 `…DesktopAgent.Runtime` **嵌套**在 `…DesktopAgent` 之下，靠 C# 外层命名空间隐式作用域；改名后嵌套关系消失 | 为受影响文件补 `using BrowserShell.Service.SDK;` |
| 3 | `RuntimeAuthenticationMode` 找不到 | 枚举放在 `.Hosting`，而 `RuntimeSettings` 在根命名空间 | 命名空间对齐 |
| 4 | 88 个文件名仍为 `Desktop*` | 首轮只替换内容未改文件名；`^Desktop` 锚点漏掉 `I*` 接口 | 二次重命名（含 `I*`） |
| 5 | 多处 sed 静默失效 | 源文件为 **CRLF**，`$` 行尾锚点不匹配 | 去掉锚点重做；并新增 `.gitattributes` 固化换行符 |
| 6 | 重复 csproj、旧 `ProjectReference` 路径 | 重生成 Runtime 时的副作用 | 删除重复项、修正路径 |
| 7 | `SoftwareHub.Auth` 依赖 | Runtime 引用 Auth 源项目 | 依赖面实测**仅 `SoftwareHubAuthenticationMode` 一个枚举**，已内联为 `ShellAuthenticationMode`，依赖完全消除 |
| 8 | 借用 Host 图标 `..\SoftwareHub.Host\SoftwareHub.Host.ico` | 跨仓文件引用 | 复制为 `Assets\BrowserShell.ico` |
| 9 | UTF-16 编码风险 | 评估 | 实测全部 UTF-8，无需转换 |
| 10 | `EnableWindowsTargeting` 污染仓库 | 我为在 Linux 上验证而加 | **已从仓库移除**，仅在本地命令行传参（你的环境是 Windows，不需要它）|

## 六、待决与未竟项

1. **命名对称性（待决）**：Page 弹窗专属的 18 个公共类型仍叫 `Window*`（`WindowOptions`、`WindowHandle`、`WindowLifecycle`…），而 Browser 侧叫 `BrowserWindow*`。这是 `DesktopWindow*` → `Window*` 机械替换的产物，`Window` 过于泛化且易与 WPF / `BrowserWindow` 混淆。
2. **SoftwareHub 侧接入（按你的要求暂缓）**：`src/SoftwareHub.Service.SDK.Hosting/Desktop/` 7 个文件、约 980 行。实测三个障碍：
   - SoftwareHub 使用的 43 个 SDK 类型中 **36 个是 internal**，原先靠 `InternalsVisibleTo` 越权访问；迁移后**必然编译失败**
   - 该适配层反向引用 `IServiceEventBus`、`ServiceHostOptions`、`ServiceInstanceIds`、`ServiceManagementMode`，迁入 BrowserShell 会**形成循环依赖**
   - `ServiceDesktopPageWindowEventSink` 是 `IServiceEventBus` 的适配器
   - 结论：它**本质属于 SoftwareHub 对 BrowserShell 的适配层**，应留在 SoftwareHub 并改为引用 NuGet 包。`AgentWindow`、`AgentClientRegistration`、`BrowserShellHubMethods` 等 36 个类型的公开化是接入的前置条件。
3. `SoftwareHub` 侧原有 `src/SoftwareHub.DesktopAgent` 与 `src/SoftwareHub.DesktopAgent.Runtime` **仍原样保留**，未做任何改动，SoftwareHub 仍可正常编译。
